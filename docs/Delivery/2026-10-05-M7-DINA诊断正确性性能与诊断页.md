## 二、关键决策

### 重复作答策略

固定使用 `latest_attempt`：同一学生同一题按 `created_at` 最新的一次作为
DINA 观测，若时间相同则按 `answer_records.id` 较大者。历史 attempt 不删除，
仍用于 `questions_done` 和 `correct_count` 统计，因此重做不会因无说明的
`question_id -> record` 覆盖而丢失证据。

### 参数来源与追踪

- 在线单题掌握度更新和完整 EM 都读取 `DINA_S_INITIAL` / `DINA_G_INITIAL`；
- 完整诊断的 `trace` 返回并保存 `algorithm_version`、`parameter_version`、
  聚合后的 `answer_count`、答题时间范围、重复策略、`converged` 和
  `iterations`；
- `diagnosis_sessions` 的新增追踪字段由 `server/sql/migrations/0002_add_dina_trace_fields.sql`
  增量迁移，不覆盖既有诊断数据。

### 查询范围对比

| 项目 | 修改前 | 修改后 |
|---|---|---|
| 答题记录 | 全表读取 `user_id/question_id/is_correct`，再在 Python 过滤 | SQL 直接 `WHERE user_id = ?`，只读 `id/question_id/is_correct/created_at` |
| 掌握先验 | 全表读取所有学生所有知识点 | SQL 直接限定当前 `user_id` 和当前 Q 矩阵属性 ID |
| 重复题 | `question_id` 字典覆盖，行为未定义 | `created_at` 最新，时间相同按 `id` 破局，并在 trace 固定策略 |

因此本次以可审计的扫描范围缩减作为性能证据；真实数据量下的耗时对比留在
M0 现场数据库验收中采集。

## 三、代码与页面

- `server/app/services/diagnosis_service.py`
  - 答题查询限定当前 `user_id`，只取诊断必要字段；
  - 当前学生和 Q 矩阵属性限定的掌握先验查询；
  - 显式 `latest_attempt` 聚合和稳定时间范围；
  - 诊断保存与 mastery upsert 仍在同一事务中。
- `server/app/models/diagnosis.py`
  - 新增 `DiagnosisTrace`，诊断结果兼容旧记录的空 trace。
- `server/app/routers/student/diagnosis.py`
  - 保留 POST 诊断；新增 GET 最近诊断，供页面恢复时间和 α 向量。
- `frontend/src/pages/diagnosis/index.vue`
  - 读取真实知识点掌握度和最近诊断；展示数据不足原因、trace 摘要和重诊入口；
  - 诊断成功后刷新掌握数据。
- `frontend/src/pages/path/path.vue`
  - 页面重新显示时重新读取路径，避免诊断成功后使用旧掌握快照。

## 五、M0 现场验收路径

1. 使用 student Token 打开 `/pages/diagnosis/index`，确认页面读取真实知识点
   列表，不再生成“知识点 ID”占位名称。
2. 对同一题先答错再答对，调用 `POST /api/student/diagnosis`，确认响应
   `trace.repeat_strategy = latest_attempt`、`answer_count` 为聚合后的题数，
   `diagnosis_sessions` 新增一条记录且 mastery 同事务更新。
3. 使用无有效答题记录的学生触发诊断，确认响应 `code=40002`、`data=null`，
   且没有新增半完整诊断会话。
4. 返回学习路径页，确认页面重新请求路径并展示新的掌握状态。

以上第 1～4 步需要已启动的 SQL Server/Neo4j 和可用测试账号，作为 M0
真实环境证据补录；本次代码、单元测试和双端构建已完成。
