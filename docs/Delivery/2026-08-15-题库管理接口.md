## 二、接口清单（对照 docs/API契约文档.md 1.2）

| 接口 | 说明 | 关键行为 |
|------|------|----------|
| `GET /api/admin/questions` | 分页查询 + 筛选 | `page`/`page_size`/`knowledge_point_id`/`type`/`difficulty_min`/`difficulty_max`/`keyword`；难度为**闭区间**筛选（含边界，可单边使用）；响应 `{list,total,page,page_size}`；列表项含契约全部字段（含 `knowledge_point_ids`/`knowledge_point_names`/`created_at`） |
| `GET /api/admin/questions/{id}` | 单个详情 | 含 `options`（JSON 解析为数组）/`answer`/`explanation`/`knowledge_point_ids`，与契约字段一一对应 |
| `POST /api/admin/questions` | 新增 | 服务端生成 ID（`q_xxxxxxxx`）；题目 + Q矩阵关联（q_matrix）同一事务写入；创建前校验关联知识点存在于 Neo4j |
| `PUT /api/admin/questions/{id}` | 编辑 | 请求体同 POST；Q矩阵全量替换（先删后插），题目更新与 Q矩阵同步在同一事务 |
| `DELETE /api/admin/questions/{id}` | 删除 | 删除题目并同步删除其全部 Q矩阵关联（同一事务） |
| `POST /api/admin/questions/batch-import` | 批量导入 | 逐行独立校验/写入，返回 `{success_count, fail_count, errors:[{row, message}]}`，单行失败不阻塞其他行 |

错误码映射：题目不存在→`40400`；参数/业务校验失败→`40000`；关联知识点不存在→`40000`（message 与契约示例一致："关联知识点不存在: kp_xxx"）；SQL Server 异常→`50001`；Neo4j 异常→`50002`（均不暴露堆栈）。

## 三、实现要点与设计决策

1. **存储职责（总则第六条）**：题干/选项/答案/解析存 SQL Server `questions` 表，选项序列化为 JSON 字符串存 `NVARCHAR(MAX)` 列（`ensure_ascii=False` 保留中文）；题目-知识点关联存 `q_matrix` 表；知识点**存在性校验**与**名称查询**走 Neo4j（`KnowledgePoint.id` 对应）。
2. **Q矩阵生命周期同步**：创建/编辑/删除均保证 `questions` 与 `q_matrix` 在同一事务（pyodbc `autocommit=False` + 显式 `commit`/`rollback`）。编辑时 Q矩阵采用全量替换（先删后插），与知识点前置依赖的「传什么就是什么」语义一致。
3. **校验全部走 Pydantic（总则第四条，不手写校验逻辑）**：
   - `type` 用 `Literal` 限定三种题型；`difficulty` 0~1；
   - 选择题选项必填且 ≥2 个、label 不重复、答案必须是选项之一；
   - 多选题答案支持 `"A, C"` 写法，`model_validator` 自动规范化为 `"A,C"`（按选项顺序）；
   - 判断题答案仅 `true`/`false`，选项缺省时自动补默认「对/错」；
   - `knowledge_point_ids` 至少 1 个（DINA 约束：Q矩阵每题至少一个知识点）且自动去重（q_matrix 有唯一约束）。
4. **批量导入的逐行统计**：请求体 `questions` 为浅校验的 dict 数组，每行在 service 中用 `QuestionCreateRequest` 深度校验，失败只记入 `errors`（行号从 1 开始、中文原因），不影响其他行——若用强类型数组，Pydantic 会让整批 422，无法产出契约要求的成功/失败统计。知识点存在性对整批只做**一次** Neo4j 查询。
5. **列表的知识点名称降级**：`knowledge_point_names` 来自 Neo4j，Neo4j 不可用时名称降级为空字符串（与 `knowledge_point_ids` 位置对齐）并记 warning，不阻塞列表查询——与知识点接口 `question_count` 的降级策略一致。
6. **异步规范（总则）**：接口全部 `async def`；同步 pyodbc/Neo4j 操作经 `asyncio.to_thread` 放入线程池；Service 层不接触 HTTP 对象；业务异常由 router 映射为业务码。
7. **不引入新依赖**：仅使用已有 fastapi/pydantic/pyodbc/neo4j/标准库。
8. **难度筛选为闭区间（契约已修订）**：初版契约只有单值参数 `difficulty`（按难度筛选，只能精确匹配）。按「先改文档、再改代码」流程，已将 docs/API契约文档.md 修订为 `difficulty_min` / `difficulty_max` 两个区间参数（含边界，可单边使用，`difficulty_min > difficulty_max` 时返回参数校验错误），实现同步改为 `difficulty >= ?` / `difficulty <= ?` 参数化条件。查询参数统一收敛到 Pydantic 模型 `QuestionListQuery`（含区间交叉校验），继续满足总则「参数用 Pydantic 校验，不手写校验逻辑」。

## 六、遗留事项与注意

1. **真实数据库端到端未验证**：本次测试全部为 mock（与知识点接口首次交付时的测试策略一致）。SQL Server 执行 `init.sql` 后，建议重点复核：分页 SQL（`OFFSET ? ROWS FETCH NEXT ? ROWS ONLY` 参数化）、`EXISTS` 知识点筛选、难度区间条件、批量导入统计与事务回滚。
2. **删除语义为硬删除**：契约与需求均要求「删除（同步删除 Q矩阵关联）」，实现为物理删除 `questions` 行 + 全部 `q_matrix` 行（同一事务）。`answer_records` 无物理外键（设计文档注释），历史答题记录会保留但题干不可读；若后续要求保留题目历史（软删除 `is_active=0`），需先改契约。
3. **ID 风格**：新题目 ID 为 `q_{8位uuid}`（如 `q_3f8a1c2b`），与 `kp_/stu_` 风格一致；`init.sql` 示例数据为 `q_001` 序号风格，两者并存不冲突。
