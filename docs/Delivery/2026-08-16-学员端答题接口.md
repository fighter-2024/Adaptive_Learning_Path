## 一、交付内容

严格对照 `docs/API契约文档.md`「2.2 答题」（接口优先级 P0：提交答案是答题核心闭环），在 `server/app/routers/student/` 下实现学员端答题接口 2 个，并同步实现 service 层：

| 接口 | 说明 | 契约章节 |
|------|------|----------|
| `POST /api/student/submit-answer` | 提交单题答案：判题 + 掌握概率更新 + 写入答题记录 | 2.2 |
| `POST /api/student/submit-batch` | 批量提交：逐题判题，返回每题结果 + 汇总统计 | 2.2 |

### 响应结构（与契约逐字段一致）

**POST /submit-answer**（data 与契约示例逐字段一致）：

```json
{
    "code": 0,
    "data": {
        "correct": true,
        "correct_answer": "B",
        "explanation": "x²-4=0 → x²=4 → x=±2，选项中 x=2 正确",
        "mastery_change": {
            "kp_001": {"before": 0.88, "after": 0.92}
        }
    },
    "message": "判题完成"
}
```

**POST /submit-batch**（契约仅定义请求体、未给出响应示例，出参按「每题的判题结果汇总」设计）：

```json
{
    "code": 0,
    "data": {
        "results": [
            {
                "question_id": "q_001",
                "correct": true,
                "correct_answer": "B",
                "explanation": "...",
                "mastery_change": {"kp_001": {"before": 0.88, "after": 0.92}}
            }
        ],
        "summary": {
            "total": 10,
            "correct_count": 7,
            "wrong_count": 2,
            "fail_count": 1,
            "correct_rate": 0.7778
        }
    },
    "message": "批量判题完成"
}
```

- `results` 顺序与入参 `answers` 一致；`summary.total` = 提交题数，`fail_count` 为判题失败题数（题目不存在/已下线），`correct_rate = correct_count / (total - fail_count)`；
- 判题失败项：`error` 给出原因（如「题目不存在」），`correct/correct_answer/explanation` 为 null，`mastery_change` 为空，**不阻塞其他题**。

## 三、关键设计决策

### 1. 判题归一化（纯函数 `judge_answer`，含单测锁定）

| 题型 | 规则 |
|------|------|
| 单选 | 去首尾空白后大小写不敏感比较（"b" 视为 "B"） |
| 多选 | 逗号拆分、去空白、大小写不敏感，**集合相等**即判对（"C,A"、"A, C"、"a,c" 均视为 "A,C"） |
| 判断 | true/false 大小写不敏感；**兼容选项文案「对/错」**（题库 answer 列存 "true"/"false"，但学生端展示的选项文案是「对/错」，不兼容会导致判断题恒判错） |

### 2. 掌握概率更新（纯函数 `bayesian_mastery_update`）

依据总则第七条「贝叶斯后验推断使用上一轮 α 作为先验」与契约 1.6 系统配置的 `dina_s_initial = dina_g_initial = 0.2`，实现 DINA 风格贝叶斯后验：

```
答对: P(α=1|X=1) = p(1-s) / (p(1-s) + (1-p)g)
答错: P(α=1|X=0) = p·s / (p·s + (1-p)(1-g)
```

- s/g 读自 `app.config.settings`（`DINA_S_INITIAL` / `DINA_G_INITIAL`，默认 0.2，符合总则 s/g ∈ [0.1, 0.3] 约束），无硬编码；
- 无掌握记录的知识点以 **0.5 中性先验**起步（常量 `DEFAULT_MASTERY_PRIOR`）；
- 结果四舍五入到 6 位小数，接口数值稳定；先验钳制在 [0, 1]；
- `user_kp_mastery` 同步累计 `questions_done`、`correct_count`（表设计 1.7 要求），掌握概率 = 贝叶斯后验；
- 该实时更新是轻量快照；**权威诊断仍由后续 DINA EM 诊断接口（POST /diagnosis）从 answer_records 重算**，两者不冲突。

### 3. 数据职责（严格遵守总则第六条）

全部落 SQL Server，未碰 Neo4j：

| 数据 | 来源 |
|------|------|
| 正确答案/题型/解析 | SQL Server `questions`（仅 is_active=1） |
| 题目-知识点关联 | SQL Server `q_matrix`（Q矩阵） |
| 答题记录 | SQL Server `answer_records`（record_id 前缀 `ar_`，对照 ID 命名规范） |
| 掌握概率快照 | SQL Server `user_kp_mastery`（upsert：有记录 UPDATE，无记录 INSERT） |

### 4. 事务与批量语义

- **单题**：answer_records 插入 + user_kp_mastery 更新在**同一事务**，任一步失败整体回滚（不会出现「记录已写但掌握未更新」的半提交状态）；
- **批量**：题目不存在（含已下线）的项记 error 跳过，不阻塞其他题；全部成功项**一次性事务写入**，数据库异常整体回滚 → 统一 50001，客户端可安全重试；
- **批次内同一知识点多题**：按提交顺序链式更新（后题的 `before` = 前题更新后的值），最终快照为链式结果（有单测锁定）；
- 已知限制：并发提交同一学生的同一知识点时存在先读后写的竞态（项目当前单学生顺序作答场景可接受），权威结果以 DINA 诊断重算为准。

### 5. 认证（写接口强制学生身份）

答题是写操作（写 answer_records / user_kp_mastery），无法像知识点读接口那样匿名降级，故本模块强制 `Depends(require_student)`：无 Token → 401，非学生角色 → 403。与 `routers/student/__init__.py` 中「后续统一开启 require_student」的占位方案方向一致，全局开启后本模块无需改动。

### 6. 错误码映射（不暴露内部堆栈）

| 场景 | 业务码 | message |
|------|--------|---------|
| 题目不存在/已下线（单题） | 40400 | 题目不存在 |
| 数据库异常 | 50001 | 数据库异常，请稍后重试 |
| 参数校验失败（Pydantic） | 40000（HTTP 422） | 统一由 main.py 校验处理器返回 |
| 批量中单题不存在 | 该项 `error` 字段 | 题目不存在（整体仍 code=0，看 summary） |

## 六、待人工确认事项（按总则第十一条，标注不自行决定）

1. **submit-batch 出参结构**：契约文档「2.2」只定义了批量接口的请求体，未给出响应示例。本次按任务要求「每题的判题结果汇总」设计了 `results + summary` 结构（见第一节）。**需人工确认后回写 `docs/API契约文档.md`**（契约约定：接口有变更必须先改文档再改代码）。
2. **掌握概率实时更新公式**：本次采用 DINA 风格贝叶斯后验（s=g=0.2、先验 0.5），符合总则第七条与契约 1.6 配置默认值，但契约未规定「单次答题 → mastery_change」的具体算法。如团队希望改用难度/耗时加权、指数滑动平均或全量 DINA EM 重算，请确认后调整（`bayesian_mastery_update` 为纯函数，单测已锁定当前行为）。
3. **无掌握记录时的 before**：契约示例中 before 恒为数字，但首次作答的知识点无历史值。本次对首答知识点以 0.5 中性先验作为 `before` 返回。如需返回 null 或隐藏该知识点，请确认。
4. **批量判题失败项的处理**：本次对「题目不存在」记入该项 error 且整体 code=0；数据库异常则整体 50001 回滚。如需「整批全部成功才返回 0」的语义，请确认。
5. **判断题答案兼容**：判题对「对/错」文案做了等价映射（见决策 1），因为题库 answer 列存 "true"/"false" 而前端展示文案是「对/错」。若前端统一提交 true/false，可移除此兼容（不影响其余逻辑）。
