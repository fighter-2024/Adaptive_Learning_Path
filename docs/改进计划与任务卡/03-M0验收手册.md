# 03 · M0 验收手册

## 1. M0 职责

M0 是本轮改进的总控和最终验收窗口，负责：

- 解释和冻结任务范围；
- 处理任务之间的接口、模型和文件冲突；
- 检查实现、测试、构建和演示证据；
- 给出通过、附条件通过或退回；
- 维护总任务看板状态；
- 组织最后的真实全链路验收。

M0 不以“代码量”验收，也不因执行者声称完成而默认通过。

## 2. 执行者交付回报格式

每张任务卡完成后，必须按以下格式回报：

```markdown
# 申请 M0 验收：M<number>

## 完成内容
- ...

## 修改文件
- path/to/file：修改目的

## 契约/数据库变更
- API：...
- SQL：...
- 配置：...

## 验证证据
- `命令` → 结果摘要
- UI 操作路径 → 截图/录屏
- 接口请求 → 关键响应

## 未完成或风险
- 无 / ...

## 与其他任务的衔接
- 需要 Mx 使用或注意：...
```

缺少验证证据的交付直接退回补充。

## 3. 通用验收门禁

### 3.1 代码和范围

- [ ] 只修改任务卡授权范围内的文件；跨范围修改有书面说明。
- [ ] 已阅读并遵守 `docs/AI开发总则.md`。
- [ ] 没有覆盖或删除他人无关改动。
- [ ] 没有遗留演示假数据、硬编码正确答案或生产凭证。
- [ ] 新依赖有理由、版本和体积/平台影响说明。

### 3.2 API 和数据

- [ ] 先改正式 API 契约，再改实现。
- [ ] 请求、响应、错误码和权限与契约一致。
- [ ] 写操作失败时事务回滚，不出现半成功状态。
- [ ] 个人数据严格按当前用户过滤。
- [ ] 数据库或图数据库异常不会被伪装成成功空数据。

### 3.3 前端

- [ ] 页面使用真实 API 数据。
- [ ] 加载、空、错误、未登录四类状态可区分。
- [ ] H5 和微信小程序构建均通过，或任务卡明确限定平台并有降级方案。
- [ ] 关键交互有截图或录屏证据。
- [ ] 不存在关键接口的静默 catch。

### 3.4 后端和算法

- [ ] Router 只负责路由、依赖和参数校验，业务在 service。
- [ ] 关键函数有类型注解和中文 docstring。
- [ ] 单元测试覆盖正常、边界和异常路径。
- [ ] 查询范围合理，无明显全表扫描或 N+1。
- [ ] 算法结果可解释、可复现，失败有明确原因。

### 3.5 安全

- [ ] 无密钥、Token、密码和连接串泄露。
- [ ] 学生接口不能获取正确答案或其他学生数据。
- [ ] 管理接口有管理员鉴权，学生 Token 不能访问。
- [ ] 日志不记录密码、完整 Token 或 API Key。

## 4. 基线验证命令

M0 根据任务影响范围执行其中一项或全部：

```powershell
cd server
python -m pytest tests -q -p no:cacheprovider

cd ../admin
npm run build

cd ../frontend
npm run build:h5
npm run build:mp-weixin
```

涉及数据库的任务还需提交：

- 正向迁移验证；
- 已有数据保留验证；
- 失败回滚或可恢复说明。

涉及 UI 的任务还需提交最少一条可复现操作路径和最终界面截图。

## 5. 核心场景验收

### 场景 A：学生真实学习闭环

1. 学生登录并刷新页面，登录状态仍存在。
2. 打开图谱，看到与该学生匹配的掌握状态和推荐顺序。
3. 点击未掌握知识点进入详情并获取真实题目。
4. 作答后由服务端返回判题和解析，数据库产生答题记录。
5. 掌握概率发生可解释变化。
6. 重新诊断后诊断页刷新。
7. 再次获取路径，结果或推荐理由与新状态一致。

### 场景 B：图谱探索

1. 树图能够按章节展开和收起。
2. 节点点击后加载局部邻居并高亮前置/后继。
3. 画布支持缩放、拖动和复位。
4. 图例与节点状态含义一致。
5. 超出节点上限时明确显示“已展示局部图谱”。

### 场景 C：管理闭环

1. 管理员登录后看到真实统计。
2. 新增或编辑知识点和前置关系后，学生图谱同步变化。
3. 新增题目并关联 Q 矩阵后，学生可获取并作答。
4. 管理端能查看该答题记录和掌握状态。

## 6. 验收结论

M0 使用以下三种结论：

- **通过**：任务卡验收项全部满足，可进入后续任务。
- **附条件通过**：核心功能正确，仅有明确记录且不阻塞下游的 P2 问题；必须登记技术债和处理任务。
- **退回**：存在契约不一致、假数据、数据安全问题、测试/构建失败或核心场景不可用。

以下情况不得附条件通过，必须退回：

- 前端硬编码正确答案或模拟接口成功；
- Token、密钥或他人数据泄露；
- 新改动导致既有测试失败；
- 数据库升级会无提示删除已有数据；
- 个性化结果实际使用匿名数据；
- 只实现页面外观，没有真实 API 闭环。

## 7. 缺陷分级和回退

| 等级 | 定义 | 处理 |
|---|---|---|
| Blocker | 无法启动、数据破坏、安全泄露 | 立即退回，停止下游合并 |
| P0 | 核心闭环错误、契约破坏、错误身份数据 | 退回，修复后重新全验 |
| P1 | 核心体验或算法解释缺失 | 原则上退回；有隔离方案时可附条件通过 |
| P2 | 样式、文案、非关键性能问题 | 可登记技术债后通过 |

执行者修复后必须说明修复范围，并重新提交受影响测试；M0 不接受“只改了一行所以不用重测”。
