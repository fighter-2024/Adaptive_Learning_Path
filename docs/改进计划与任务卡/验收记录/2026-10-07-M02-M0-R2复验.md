## 3. 实际模块行为：6 通过、4 反例失败

独立载入**当前生产 user.js + request.js、实际 Vue/Pinia**；只适配别名/BASE_URL 与 store 绑定，uni.request 用受控回调提供响应时序。没有复制会话逻辑作为被测对象，没有向浏览器或后端注入认证。合成身份/Token 仅在 Node 进程，不是真实凭证。

通过：

- 无 Token 初始化完成后，正式 login 方法及后续验证返回 true。
- 并发初始化实际仅发一个 transport 请求。
- 实际请求网络失败之后能重试成功。
- 当前错误/过期401形状和管理员角色仍拒绝并清空会话。
- 旧初始化成功晚到时，不覆盖 B，不清除 B 正在执行的 Promise；两个 B 并发调用正确复用。

剩余反例：

| 优先级/案例 | 实际结果 | 预期 |
|---|---|---|
| P1：A登录 POST 在途，B后发完成，再返回A旧POST及用户 | 最终 user=controlled-a | 保持 B |
| P1：A登录 POST 在途时退出，再返回旧POST及用户 | logged_in=true/A，退出被撤销 | 保持退出 |
| P2：A旧 /auth/me 在途，切换B，旧HTTP401/40100晚到 | B被清空，跳 `/pages/auth/login` | B保持登录 |
| P2：相同时序，旧HTTP200/业务40101晚到 | B被清空并跳转 | B保持登录 |

第一类因 sessionVersion 在 POST 返回之后才递增，旧响应被当成一次新登录；第二类因 request.js 的 clearStudentSession 无请求所属会话检查，副作用发生在 user.js catch 的版本校验之前。这不是后端认证改动；客户端仍可能采用已被替换的有效账号，或错误清除新会话。

完整实证：[实际模块行为 JSON](../../Delivery/2026-10-07-M02-M0-R2-client-evidence.json)。这些是受控客户端时序试验；**不冒称已用浏览器自然重现四种延迟响应**。普通冷登录/切换的真实 UI 与 SQL 是上一节独立证据。

当前 verify-session-init 在静态正则检查之后，只运行脚本内 createSessionModel；未调用真实 login 或请求封装。因此脚本 PASS 不能代替生产模块结果。M0-R3 要求修正两处副作用并把门禁改为真实模块行为测试，避免复制实现后自证通过。
